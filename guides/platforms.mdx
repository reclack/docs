checkout reaches a payer in one of three ways, and all three work anywhere you
can put a link, paste an embed or call an HTTP endpoint.

## The three ways in

Pick by how much of the payment you want happening on your own page.

### A link

A [payment link](/guides/payment-links) is a URL you create once and reuse. It
takes one-time or recurring payments, and it goes anywhere a URL goes: a
product description, a button, a pinned message, an email.

```bash
curl -X POST "https://api.reclack.com/v1/payment-links" \
  -H "Api-Key: $RECLACK_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Premium Research Access",
    "type": "fixed",
    "price_id": "price_7Fh2PqX9",
    "collect_email": true
  }'
```

Use a link when the platform runs its own checkout and will not let you
replace it, or when there is no server of yours behind the page at all.

### An embed

The [checkout widget](/sdks/checkout-widget) puts our checkout inside your own
page, so the buyer never leaves your site. It runs in a frame served from our
domain, which means the amount and the address they approve cannot be read or
changed by anything else on the page.

```html
<div id="checkout"></div>
<script src="https://js.reclack.com/widget.js"></script>
<script>
  Reclack().launch("chk_7Fh2PqX9Lm", {
    mode: "inline",
    container: "#checkout",
  });
</script>
```

Any platform with a custom code or HTML block can host this. One thing to do
first: add your site's address under **Developers** then **Embedding** in the
dashboard. Until you do, the frame loads but refuses to show anything payable.

### The API

[Create a checkout session](/guides/checkout) from your own server when the
price, the customer or the reference you attach is only known at the moment
somebody buys. This is what our Whop app does, and what any platform that lets
you run code on a purchase can do.

## Knowing when a payment lands

Give the customer what they bought when the [webhook](/webhooks/overview)
arrives, not when their browser comes back to your page.

The browser often does not come back. People close the tab as soon as their
wallet says the payment went through, lose signal on the way, or pay on a
phone while your page sits open on a laptop. The webhook arrives anyway, and
we keep retrying it until your server answers.

Every event names the things it points at and repeats the `metadata` you set
on the checkout, so one event tells you which order, member or subscriber it
belongs to without a second API call.

```json
{
  "id": "evt_9KdP2mWq",
  "type": "checkout.completed",
  "data": {
    "id": "chk_8Qd2Lm",
    "customer_id": "cus_4Rb1Nt",
    "subscription_id": "sub_2Yh7Kp",
    "metadata": { "order_id": "ord_1982", "platform_user_id": "u_4471" }
  }
}
```

If the platform has an automation layer, point the webhook straight at it. A
Zap, a scenario or a workflow receives exactly the payload your own server
would, so you can grant access without running a server at all.

<Tip>
  Put the platform's own id for the buyer on the checkout's `metadata`. You
  get it back on that checkout's event and on every later event about the
  subscription it created, which is all you need to match a renewal months
  from now to the right account.
</Tip>

## Letting people in, and out again

Nearly every platform integration ends the same way: money arrives, and
somebody should now be able to get at something. Four events cover the whole
life of that.

<Steps>
  <Step title="Send them to pay">
    Create the checkout with the platform's id for the buyer in `metadata`,
    then send them to the `url` it returns.
  </Step>
  <Step title="Let them in">
    When `checkout.completed` or `subscription.created` arrives, read that id
    back out of `metadata` and grant access to whoever it names.
  </Step>
  <Step title="Keep them in while they keep paying">
    `subscription.renewed` tells you the next charge date in `next_charge_at`.
    Set access to run out on that date. Do not add a month yourself: billing
    runs on fixed spans rather than calendar months, so a date you work out by
    hand slowly drifts away from the one the buyer agreed to.
  </Step>
  <Step title="Stop when they stop">
    `subscription.cancelled` means no further charges are coming. They keep
    access until the period they already paid for runs out.
  </Step>
</Steps>

## Whop

Reclack ships an app for [Whop](https://whop.com). A community owner installs
it, connects their Reclack workspace with an API key, and sells one-time or
recurring stablecoin access from a panel in their own sidebar. Paying can also
grant a membership on the creator's Whop product, so the buyer gets the
Discord roles and course access attached to it.

The app is the worked example of everything above: checkout from a server,
metadata carrying the platform's user id, and fulfilment on the webhook.

## Anywhere else

Nothing on this page is a closed list. If a platform lets you put a URL in
front of a customer, it works today. If it lets you run code when something
happens, it works better.

Start with the [quickstart](/quickstart), or read how
[subscriptions](/guides/subscriptions) are authorized if recurring is what you
are after.
